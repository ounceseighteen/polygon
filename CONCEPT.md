# Полигон рефакторинга — общая концепция

## Что это
Практическое задание: 25 команд получают одинаковое legacy-приложение
на Flask + Python + SQLite и за ограниченное время улучшают его
по измеримым метрикам, не сломав функциональность.

## Формат
- 25 команд, 2–5 человек.
- Изолированные папки и порты: team01 → :5001, ..., team25 → :5025.
- Судья запускает своё Flask-приложение на :8080 и управляет
  всем через браузер.
- Никаких Docker, Gunicorn, k8s. Только python app.py и локальные скрипты.

## Что даётся на старте
- Репозиторий legacy_app: app.py, templates/, static/, seed.py.
- Намеренно плохой код: сырой SQL, N+1, отсутствие индексов,
  except: pass, print вместо логов, секреты в коде, дублирование.

## Функционал (нельзя менять)
- GET  /              — HTML-список товаров
- GET  /api/items     — JSON-список
- POST /api/orders    — создание заказа
- GET  /api/report    — отчёт за период

## Метрики
- Скорость ответа (p95 на /api/items и /api/report)
- Покрытие тестами
- Качество кода (ruff, radon, дублирование)
- Число ошибок в app.log на 1000 запросов
- Безопасность (bandit, отсутствие f-string SQL)
- Читаемость и структура проекта

## Что запрещено
- Менять публичный API и формат ответов.
- Удалять функционал ради метрик.
- Хардкодить ответы под тесты.
- Отключать логирование ошибок.
- Подменять tools/bench.py, tools/check_logs.py,
  tools/acceptance_tests.py.

## Что разрешено
- Любой рефакторинг внутри Flask + Python + SQLite.
- Индексы, WAL, пагинация, кэш в памяти.
- Разбиение app.py на модули и blueprints.
- Свои тесты, логирование, config.py.

## Оценка
Автоматическая, от 2 до 5. Сначала gate (acceptance),
потом score по метрикам, потом перевод в оценку.
Подробности — в JUDGE.md.

## Этапы
1. Kickoff: правила, baseline, доступы.
2. Работа команд.
3. Финальный замер судьёй.
4. Demo и защита.
5. Постмортем: какие приёмы дали максимальный прирост.
